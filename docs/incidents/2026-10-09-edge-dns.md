## 3. Root cause

Several independent conditions each had to hold. Removing any one of them would have stopped the outage.

1. **The bootstrap state exported an empty `cloudflare_zone_id`.** `live/bootstrap` declared the variable with
   `default = ""` and exported it. The value reaches it only through `TF_VAR_cloudflare_zone_id`; an apply without
   that variable writes `""`. (Confirmed: the CI plan on 2026-10-12 shows `cloudflare_zone_id = "" -> "88f6da28..."`
   for bootstrap, i.e. the state output is empty today.)
2. **Every consumer read that output with no check.** `live/edge` and `live/storage-*` took the zone id from
   `data.terraform_remote_state.bootstrap.outputs.cloudflare_zone_id`. An empty output is not an error to
   OpenTofu; it is a value.
3. **`zone_id` forces replacement** on `cloudflare_record` (and on `cloudflare_r2_custom_domain`). A changed zone id
   is therefore a destroy-then-create, and the provider destroys first.
4. **The re-create could not succeed** because it carried the same empty zone id. A replace that fails halfway is an
   outage, not a no-op.
5. **Nothing read the plan.** The Plan check passes whatever the plan contains ("Plan required" = it ran). The PR
   author had it in front of them; merging applied it, and the apply workflow applies the plan it has just made.
6. **Nothing was watching.** Drift detection had no Cloudflare credentials, so it was permanently red for these
   stacks and had no alert beyond a failed run.

The Renovate bump was the *trigger*, not the cause. A lock bump is a no-op for the configuration, but it was the first
change under `live/edge` after the bootstrap output went empty (one Apply run in between, with `edge` skipped), so it
was the first time the empty value was ever planned against the records. #150 hit `storage-dev` the same way and is
not a Cloudflare v5 problem: the plan under v5.27.0 is clean once the zone id is real (section 6).

## 4. How the bootstrap output became empty

**Confirmed:** CI wrote the right value at 14:45 on 2026-09-22; the object was modified again at 14:53:33; the state
today holds `""`.

**Strong evidence for the cause:** the state also holds an IAM trust document for `qnsc-chart-publish` with two
`sub` patterns (`repo:quynhonsemiconductor/gitops:ref:refs/tags/chart-v*` and a `repo:quynhonsemiconductor@*/gitops@*`
form). The second pattern appears in **no commit in any branch** of this repository (`git log --all -S'@*/gitops@*'`
is empty), while the config on `main` has one. So the later write was made from a configuration that was never
committed, without `TF_VAR_cloudflare_zone_id`. That is what a `tofu apply` run locally in `live/bootstrap` looks like.

**Not yet confirmed:** who ran it, from where, and the exact version. That needs S3 object-version metadata
(`list-object-versions` for `platform/bootstrap/terraform.tfstate`: LastModified, VersionId, Size, IsLatest only, never
the content) and CloudTrail management events for the writer. The operating session had expired (MFA), so those two
checks are **open**. Until they are done this paragraph is a well-supported hypothesis, not a finding.

Note for the owner: this also means merging infra#161 will apply that bootstrap config from CI and **narrow** the
`qnsc-chart-publish` trust to the single pattern in git. The second pattern appears to have been added for GitHub's
immutable subject claim (`gitops` has `use_immutable_subject: true`). If chart publishing from CI must keep working
under that claim, add the pattern to `live/bootstrap/chart-publish-role.tf` in the same change. CI publishing is
being replaced by GHCR (the ECR chart registry is to be dropped), so this may not matter; it is a decision, not an accident.

## 5. What changes

| Fix | Where | What it prevents |
| --- | --- | --- |
| `cloudflare_zone_id` is a required, validated (`^[0-9a-f]{32}$`) variable in `edge`, `storage-dev`, `storage-prod`, set from `vars.CLOUDFLARE_ZONE_ID` by CI; no remote-state read | infra#161 | causes 1, 2 |
| bootstrap: variable has no default; output has a `precondition` | infra#161 | the product repos reading an empty output |
| `prevent_destroy` on every DNS record, the Pages project and domains, the SES identity; precondition on the zone id | infra#161 | cause 3: a replace stops the plan |
| the apply and plan workflows refuse a plan that deletes or replaces a DNS or identity resource unless the PR has the label `allow-dns-destroy`; allowed addresses go to the job summary | infra#163 | causes 4, 5 |
| Renovate: no automerge for OpenTofu providers/modules, `read-the-plan` label, providers aged 3 days, majors in their own PR on request | infra#164, tf-modules#159 | cause 5 |
| drift: read-only Cloudflare token (`CLOUDFLARE_API_TOKEN_READONLY`), failure opens an issue and posts to Teams | infra#162 | cause 6 |

Trade-off of `prevent_destroy`: it also blocks a *deliberate* replacement. To rename or recreate a record, delete the
line in the same reviewed change. OpenTofu 1.9.1 (pinned) does not allow a variable in `lifecycle`, so it is a literal.

Still the owner's: required reviewers on the `shared` environment (none today), creating
`CLOUDFLARE_API_TOKEN_READONLY`, confirming the SNS subscription for `qnsc-security-alerts`.

## 7. The ACM certificate `*.qnsc.vn`

`arn:aws:acm:ap-southeast-1:608983206583:certificate/c3a479c8-f7b4-4bf1-b26c-998e14a34384`, expiring 2027-01-26.
It is created by `live/edge` (`aws_acm_certificate.wildcard`, output `acm_cert_arn`) and consumed only by the shared
ALB module in `live/runtime-dev` and `live/runtime-prod`; both stacks default `enable_alb = false`. The EKS spike does
not use it (Cloudflare Tunnel ingress), and the inventory shows `InUse: False`. It is **not** part of the spike
teardown. `RenewalEligibility=INELIGIBLE` is expected for a certificate that is not in use; ACM manages renewal only for
certificates that are in use, so attaching it to something is what would make it eligible; I have not tested that. Not verified with `describe-certificate` (session expired).
